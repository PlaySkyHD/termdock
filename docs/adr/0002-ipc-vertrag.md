# ADR 0002: IPC-Vertrag zwischen Client und Core

Status: angenommen (13.11.2026)

## Kontext

Fenster und Core sind getrennte Prozesse (ADR 0001). Ausgabe kann sehr groß werden (Abnahme 11). Der Vertrag muss in `packages/protocol` liegen und von Core und Desktop gleich verwendet werden.

## Entscheidung

- **Transport:** Windows Named Pipe `\\.\pipe\termdock-core-<benutzer>-<hash>` (ein Name je Konto). Kein TCP. In Tests ein eindeutiger Pipe-Name je Test.
- **Zugriff:** Der Core nutzt den Standard-Sicherheitsdeskriptor von libuv (Node bietet keine eigene DACL, Messung im archivierten Change `secure-core-pipe`, `design.md`). Er gibt SYSTEM, Administratoren und dem aktuellen Benutzer Vollzugriff und Everyone und Anonymous nur Lesezugriff. Kein fremdes Konto kann schreiben, also keine Anfrage senden und keine Events erhalten; lesendes Öffnen bleibt möglich. Der Core trennt Verbindungen ohne `hello` nach 5 s, und ein Windows-Test prüft die DACL der echten Pipe. Soll auch das Öffnen verboten werden, braucht es ein Native-Modul mit `CreateNamedPipe` und eigener DACL (eigener Change).
- **Rahmung:** Längenpräfix. Jeder Frame ist `uint32 BE Länge des Headers | Header (UTF-8-JSON) | uint32 BE Länge der Nutzdaten | Nutzdaten (Bytes)`. Terminal-Ein- und -Ausgabe stehen als rohe Bytes in den Nutzdaten, nicht als Base64 im JSON. Maximale Headergröße 1 MiB, maximale Nutzdaten 4 MiB; größere Frames sind ein Protokollfehler.
- **Nachrichtenarten im Header** (`kind`):
  - `request` mit `id`, `method`, `params`; Antwort `response` mit gleicher `id` und `result` oder `error { code, message }`.
  - `event` ohne `id` vom Core an Clients (z. B. `session.output`, `session.stateChanged`, `view.writerChanged`, `session.created`, ab 1.3 `session.updated`, `session.removed`, `workspace.changed`, `profile.changed`, `settings.changed`).
- **Versionierung:** Erste Nachricht jedes Clients ist `hello { protocolVersion, clientId, clientKind }`. Der Core antwortet mit seiner `protocolVersion`; bei Unterschied in der Hauptversion `error { code: "protocol_mismatch" }` und Verbindungsabbau. Neue optionale Felder erhöhen die Nebenversion: 1.1 ergänzt `outputSeq` im Ergebnis von `session.attach` und `seq` in `session.output` (Grenze zwischen Snapshot und Live-Ausgabe, ADR 0003, #34). 1.2 ergänzt das Event `session.created { session }` (#46): Der Core sendet es nach `session.create` an jede Verbindung, die `session.list` genutzt hat (wie `session.stateChanged`), auch an den Anleger, vor dessen Antwort und im Zustand `Starting`. „Abgelehnt“ (kein Event) heißt vor dem Eintragen (`bad_request`, Shutdown, Speicherfehler); scheitert der Start danach, kommt das Event und `session.stateChanged` mit `Interrupted` folgt. Sessions, die der Core beim Start lädt, meldet er nicht (Clients nutzen `session.list`). Er filtert nicht nach der Version des Clients: Ein Client mit älterer Nebenversion verwirft ein Event, das sein Parser nicht kennt, und bleibt verbunden (die Client-Bibliothek tut das). Clients müssen unbekannte Events ignorieren. 1.3 ergänzt die Methoden und Events der Phase 3 (#55, siehe unten) und macht `launch` in `session.create` optional, wenn `profileId` gesetzt ist; bestehende Methoden und Events bleiben unverändert.
- **Methoden in V1 (Phase 1):** `session.create`, `session.list`, `session.attach` (legt eine View an, liefert Snapshot), `session.detach`, `session.input` (nur von der schreibenden View), `session.resize` (nur von der schreibenden View), `session.claimWriter`, `session.kill`, `core.shutdown`. Phase 2 ergänzt `layout.get` (liefert `{ layout?, revision }`) und `layout.save { layout, baseRevision? }` (liefert `{ revision }`; ein veraltetes `baseRevision` ergibt `invalid_state`). Es gibt ein globales Layout und deshalb kein Event `layout.changed`.
- **Methoden der Phase 3 (1.3, #55):** `workspace.list|create|update|delete`, `project.create|update|delete`, `profile.list|create|update|delete`, `session.update { sessionId, name?, workspaceId?: string | null, loggingEnabled? }`, `session.archive`, `session.delete`, `settings.get`, `settings.set { settings }` (Teiländerung) und `history.search { query, sessionIds?, limit? }` (liefert `{ hits, truncated }`). `*.create` und `*.update` liefern das geänderte Objekt, `*.list` die vollständige Liste, `*.delete` und `session.archive` `{}`. In Updates heißt ein fehlendes Feld „unverändert“ und `null` „entfernen“; neue Anfragen lehnen unbekannte Felder ab. Der Core prüft das zusammengeführte Objekt vor dem Speichern mit `validateWorkspace`, `validateProject`, `validateLaunchProfile` bzw. `validateSettings`, damit kein Client eine gespeicherte Liste ablehnt. Die Typen (`Workspace`, `Project`, `LaunchProfile`, `Settings`, `HistoryHit`) und Grenzen (Namen 128 Zeichen, Pfade 512, 64 Workspaces mit je 16 Projekten und höchstens 12 KiB JSON, 64 Profile zu je 8 KiB, Suche 256 Zeichen und 200 Treffer) stehen in `packages/protocol/src/model.ts`. Events: `workspace.changed { workspaces }` und `profile.changed { profiles }` mit der vollständigen Liste, `session.updated { session }`, `session.removed { sessionId }`, `settings.changed { settings }`; Empfänger wie bei `session.created` sind alle Verbindungen, die `session.list` genutzt haben. Bis die Fach-Issues (#56–#64) sie umsetzen, beantwortet der Core jede dieser Methoden mit `internal` „noch nicht umgesetzt“.
- **Fehlercodes** sind stabile Strings: `protocol_mismatch`, `bad_request`, `not_found`, `not_writer`, `invalid_state`, `backend_unavailable`, `internal`.
- Schemas als TypeScript-Typen mit Laufzeitprüfung an der Pipe-Grenze (handgeschriebene Guards, keine Schema-Bibliothek, bis ein OpenSpec-Design etwas anderes begründet).

## Folgen

- Die Desktop-App leitet Renderer-Nachrichten über Preload und Main an die Pipe weiter. Der Renderer hat keinen direkten Pipe-Zugriff.
- Der Codec ist reine Logik und wird ohne Pipe getestet (Teilframes, mehrere Frames pro Chunk, Übergröße).
