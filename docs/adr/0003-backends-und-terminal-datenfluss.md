# ADR 0003: Backends und Datenfluss zum Terminal

Status: angenommen (13.11.2026), durch Phase 0 bestätigt und präzisiert (`docs/poc/phase-0-bericht.md`)

## Kontext

Dieselbe Session soll in mehreren Fenstern sichtbar sein, aber nur eine View schreibt und bestimmt die Größe (Kapitel 7). WSL-Sessions sollen über tmux langlebig sein (Kapitel 4).

## Entscheidung

- **Eine PTY pro Session im Core, nicht pro View.** Der Core hält für jede laufende Session genau eine PTY (node-pty/ConPTY). Er verteilt deren Ausgabe als `session.output`-Events an alle Views der Session. Views sind reine Darsteller (xterm.js).
- **WSL-Backend:** Die PTY führt `wsl.exe -d <distro> --cd <linux-verzeichnis> --exec tmux -L termdock -T RGB new-session -A -s td-<sessionId> [befehl] ; set-option -t td-<sessionId> status off` aus (Argument-Array, `;` als eigenes Argument). `--exec` statt `--`, weil wsl.exe die Argumente nach `--` an die Login-Shell der Distro weiterreicht (`$HOME`, `;` usw. würden interpretiert, Phase 0). `-T RGB`, weil tmux sonst 24-Bit-Farben auf 256 Farben herunterrechnet. Eigener tmux-Socket `termdock`, damit Nutzer-tmux unberührt bleibt. tmux-Option `status off` im selben Aufruf, sonst meldet die Session eine Zeile weniger als die PTY. Wiederanbinden = neue PTY mit `tmux -L termdock -T RGB attach-session -t td-<sessionId>`. Existenzprüfung über `tmux -L termdock has-session -t td-<sessionId>` (ohne PTY, per `execFile`).
- **WSL am Leben halten:** WSL beendet eine Distro samt tmux-Server, wenn kein `wsl.exe`-Prozess mehr läuft (Phase 0: nach 8 s ohne `wsl.exe` lebte die Session noch, nach 20 s und 90 s war sie weg). Der Core hält deshalb je Distro mit laufenden Sessions einen Keepalive-Prozess `wsl.exe -d <distro> --exec sleep infinity` (ohne PTY) und beendet ihn, wenn die letzte Session der Distro endet.
- **node-pty:** offizielles `node-pty` mit den mitgelieferten N-API-Prebuilds (`win32-x64`), dieselbe Binärdatei für Node und Electron, kein Rebuild. `useConptyDll: true` (mitgelieferte ConPTY). Die ConPTY fragt beim Start Device Attributes (DA1) ab und wartet bis zu 3 s auf Antwort; die WSL-PTY beantwortet diese erste Abfrage deshalb selbst (siehe Präzisierungen).
- **Windows-Backend:** Die PTY führt die Shell direkt aus (`pwsh.exe`, `powershell.exe`, `cmd.exe`). Persistenz nur so lange wie der Core läuft (ADR 0001).
- **Snapshot für neue Views:** Beim `session.attach` liefert der Core einen Snapshot: bei WSL `tmux capture-pane -p -e -J -S -<n>` des sichtbaren Bereichs plus Cursorposition, bei Windows den Inhalt eines begrenzten Rohdaten-Puffers im Core (256 KiB je Session). Danach folgen Live-Events; die Grenze dazwischen ist exakt (siehe „Grenze zwischen Snapshot und Live-Ausgabe“).
- **Größe:** Nur die schreibende View sendet `session.resize`. Der Core ändert die PTY-Größe (tmux folgt dem einzigen Client). Lesende Views bekommen die maßgebliche Größe mit `session.resized` und stellen das Terminal in dieser Größe dar.
- **Lesende Views: beschnitten, nicht skaliert (Entscheidung der offenen Frage, Phase 2, #27).** Ein Leser zeigt das Terminal in Spalten und Zeilen des Schreibers in normaler Schriftgröße. Ist seine Fläche kleiner, wird es rechts und unten abgeschnitten; die Fläche außerhalb des Terminals ist abgedunkelt, und ein Hinweis nennt „Größe des Schreibers: C×R“. Skalieren wurde verworfen: Bei kleinen Panes würde die Schrift unlesbar, und Zeichen auf Bruchteilen von Pixeln verfälschen Box- und Liniengrafik von TUIs. Wer die ganze Fläche braucht, übernimmt das Schreibrecht (Klick ins Pane), dann bestimmt seine Fläche die Größe.
- **Backend-Schnittstelle** (`packages/core/src/backend/types.ts`): `start`, `attach`, `exists`, `kill`, `snapshot`, optional `resolveLaunch` und `redraw`, plus eine `PtyHandle` mit `write`, `resize`, `onData`, `onExit`, `dispose`. Tests nutzen `FakeBackend`.

### Präzisierungen aus der Umsetzung (#4, #13)

- **Exakte tmux-Ziele:** Alle Aufrufe adressieren die Session als `=td-<id>` (Pane-Ziele `=td-<id>:`), damit `td-1` nie `td-10` per Präfix trifft. Session-IDs bestehen nur aus Buchstaben, Ziffern, `-` und `_`.
- **Exit-Code über `remain-on-exit`:** Der Start setzt im selben Aufruf `set-option -w -t =td-<id>: remain-on-exit on` und `set-hook -t =td-<id>: pane-died "detach-client -s =td-<id>"`. Endet das Programm, bleibt das Pane tot stehen, der Client wird getrennt, und das Backend liest `#{pane_dead_status}` (bei Signal `128 + Signal`), meldet den Exit-Code und entfernt die Session mit `kill-session`. Ein lebendes Pane nach dem Client-Ende heißt: nur der Client ging verloren (Ende ohne Exit-Code).
- **DA1 in der PTY:** Solange von außen keine DA1-Antwort (`ESC [ ? … c`) geschrieben wurde, beantwortet die WSL-PTY die erste Abfrage `ESC [ c` selbst mit `ESC [ ? 1 ; 2 c` und entfernt sie aus der Ausgabe. So warten Start und Wiederanbinden nicht auf eine View, und keine View antwortet doppelt.
- **Maskierung von `;`:** tmux liest ein Argument, das auf `;` endet, als Befehlstrenner. Das Backend setzt vor ein solches abschließendes `;` genau einen Backslash (tmux entfernt ihn wieder), für `command`-Argumente und `-e`-Umgebungswerte. Ein einzelnes `command`-Argument läuft über `env --`, weil tmux es sonst an `sh -c` gibt.
- **`--cd ~` außer beim Start:** `attach-session`, `has-session`, `kill-session`, `capture-pane` und `display-message` laufen mit `--cd ~`, damit ein gelöschtes Arbeitsverzeichnis das Wiederanbinden nicht verhindert. Nur `new-session` nutzt `LaunchSpec.cwd`.
- **Keepalive-Backoff:** Stirbt ein Keepalive, während Sessions seiner Distro bekannt sind, startet das Backend ihn nach 1 s, 2 s, … höchstens 60 s neu; nach mehr als 30 s Laufzeit beginnt die Wartezeit wieder bei 1 s. `WslBackend.dispose()` beendet alle Keepalives, die tmux-Sessions bleiben.
- **Distro festhalten:** Fehlt `LaunchSpec.distro`, löst `resolveLaunch` sie beim Start auf (konfigurierte, sonst Standard-Distro) und die Registry speichert sie. Ein späteres `wsl --set-default` ändert nicht, wo der Core die Session sucht.
- **Verlorener Client:** Endet eine PTY ohne Exit-Code, prüft die Registry `exists` und hängt eine neue PTY an (höchstens 3 Versuche: sofort, nach 0,5 s, nach 2 s); Zustand, Views und Schreiber bleiben. Erst wenn die Session fehlt oder alle Versuche scheitern, wird sie `Interrupted`. Windows-Backends melden nach dem Ende ihrer PTY `exists = false` und werden wie bisher `Interrupted`.
- **Cursor im Snapshot (#32):** Das WSL-Backend fragt Bildschirm, Cursorposition und Sichtbarkeit (`#{cursor_flag}`) in einem tmux-Aufruf ab und hängt an den Bildschirm `ESC[0m` (Attribute zurücksetzen), `ESC[<y+1>;<x+1>H` und `ESC[?25h` bzw. `ESC[?25l` (tmux meldet den Cursor verborgen, z. B. htop). Die Position steckt in den Nutzdaten; das Feld `cursor` bleibt. Der Windows-Rohpuffer hat keinen Cursor und bleibt unverändert.
- **Terminal-Modi im Snapshot (#42):** tmux setzt die Modi seines Clients einmal beim Start (`ESC[?1h ESC=` aus `smkx`, `ESC[?2004h`; die ConPTY dazu `ESC[?1004h`) und Mausberichte bei `mouse on` (`ESC[?1006h ESC[?1000h ESC[?1002h`); eine später angehängte View sah diese Bytes nie. Die tmux-Formate helfen nicht, sie beschreiben das Pane und nicht den Client (gemessen mit tmux 3.6: `mouse on` und `less` ergeben `mouse_any_flag=0`, `keypad_cursor_flag=1`; ein Format für Bracketed Paste fehlt). Die Registry verfolgt deshalb in der Ausgabe jeder Session Application Cursor Keys, Application Keypad, Mausprotokoll und -kodierung, Fokusberichte und Bracketed Paste (`session/terminal-modes.ts`, im selben Schritt wie `outputSeq`) und stellt dem Snapshot die Sequenzen der eingeschalteten Modi voran, für tmux-Bildschirm und Rohpuffer. Die View schreibt nach `reset()` also Modi, Bildschirm, dann `ESC[0m`, Cursor und Sichtbarkeit. Erzeugt werden nur Sequenzen aus dieser festen Liste (Mauskodierung nur SGR `1006` und `1016`, die übrigen ignoriert xterm.js). Fokusberichte, die der Schreiber daraufhin sendet, schluckt die ConPTY (gemessen mit `cat -v`); sie erreichen das Programm nicht. Beim Binden einer neuen PTY beginnt der Parser neu, die Modi bleiben. Alternate Screen, Cursorform und `win32-input-mode` (`?9001`, xterm.js kennt ihn nicht) bleiben außen vor. Ein Neustart setzt die Modi mit dem Rohpuffer zurück. Protokoll und `PROTOCOL_VERSION` bleiben unverändert; die Umgehung `bracketedPaste` im Terminal-Controller (#28) entfällt.
- **Grenze zwischen Snapshot und Live-Ausgabe (#34):** Die PTY-Ausgabe (tmux-Client, dann ConPTY) läuft dem tmux-Server hinterher, `capture-pane` bildet den Server ab. Früher hängte die Registry die Ausgabe der Aufnahme an den Snapshot; der Bildschirm enthielt sie oft schon, sie erschien doppelt (gemessen: `… 144 145 142 143 144 145 146 …`). Jetzt nummeriert die Registry die Ausgabe je Session (ab 1, über PTY-Wechsel hinweg) und registriert die View im selben Schritt, in dem sie die Marke liest (`outputSeq`, Protokoll 1.1, ADR 0002); der Snapshot bleibt unverändert. Ausgabe der Aufnahme bekommt die View nicht. Damit ist die Grenze im Strom des Core exakt, aber nicht zu `capture-pane` (ohne Neuzeichnen fehlt Ausgabe, gemessen: `146 149`). Deshalb fordert die Registry nach dem Registrieren `redraw` an, wenn der Snapshot vom Backend kam: Das WSL-Backend ruft `list-clients -F '#{client_tty}'` und je Client `refresh-client -t <tty>` auf (eine Session als Ziel kennt `refresh-client` nicht). tmux schreibt das Neuzeichnen hinter alles Bisherige in den Client-Strom; es kommt vollständig durch die ConPTY 1.23 (`ESC[H`, jede Zeile mit `ESC[K`, Cursor) und überschreibt, was doppelt kam oder fehlte. Das Neuzeichnen wird nicht abgewartet, ein Fehler lässt das Anhängen nicht scheitern. Jeder Client wird einzeln neu gezeichnet, ein inzwischen getrennter Client hält die übrigen nicht auf. Je Session läuft höchstens ein Neuzeichnen; Anforderungen währenddessen (mehrere Panes beim Wiederherstellen, #29) ergeben genau ein weiteres danach. Ein gescheitertes Neuzeichnen wird einmal wiederholt, danach meldet die Registry es auf stderr (`onRedrawError`); die View behält dann bis zum nächsten Neuzeichnen ihren Snapshot. Bis es ankommt (zwei `wsl.exe`-Aufrufe), kann die neue View kurz falsche Zeichen zeigen; alle Views der Session sehen dasselbe Bild noch einmal. Der Rohdaten-Puffer braucht kein Neuzeichnen, er wird im Schritt des Registrierens kopiert. Beobachtung: tmux zeichnet auch von selbst neu, etwa beim Wechsel des Vordergrundprogramms; das verdeckte den Fehler oft.
- **node-pty-Eingabepipe:** node-pty 1.1.0 hängt an die ConPTY-Eingabepipe keinen `error`-Listener. Eingabe an einen gerade beendeten Client scheitert asynchron mit `EAGAIN`; `spawnPty` fängt diesen Fehler ab, sonst beendet er den Core.

## Folgen

- tmux sieht immer nur einen Client, Größenkonflikte zwischen Fenstern entstehen nicht in tmux.
- node-pty 1.1.0 bringt Prebuilds mit und läuft unter Node 25 und unter Electron 45 (auch mit `ELECTRON_RUN_AS_NODE=1`). Ein Bau aus dem Quelltext braucht node-gyp ≥ 12 (VS 2026) und die MSVC-Spectre-Bibliotheken; er ist nicht nötig.
- Wer die Session anzeigt, muss Terminal-Abfragen beantworten (DA1, Cursorposition). Das tut nur die schreibende View; lesende Views verwerfen ihre automatischen Antworten.
