# ADR 0006: Desktop-Architektur

Status: angenommen (13.11.2026)

## Kontext

Phase 2 (Kapitel 12) bringt die Oberfläche: Sidebar, Tabs, 2–4 Split-Panes, Tastenkürzel und Layout-Wiederherstellung. Fenster sind Clients des Core (ADR 0001) und sprechen nur über die Pipe mit ihm (ADR 0002). Der PoC aus Phase 0 (`poc/`) hat Electron 45.3.1 mit xterm.js 6.0.0, `contextIsolation`, `sandbox` und CSP geprüft. Die Struktur muss #26 (Sidebar/Tabs), #27 (Splits), #28 (Keymap) und #29 (Layout-Wiederherstellung) tragen, ohne dass dieses Gerüst ihre Funktionen vorwegnimmt.

## Entscheidung

- **Stack:** Electron 45.3.1 (wie im PoC), React und TypeScript, ohne UI-Bibliothek. Eigenes CSS im Stil von VS Code (Dark+). Der Renderer wird mit Vite gebaut (`dist/renderer`, relative Pfade, kein Inline-Skript), Main und Preload mit `tsc -b`. Paket `apps/desktop`, Start mit `npm start -w apps/desktop`.
- **Aufteilung:** Main (`src/main`), Preload (`src/preload`, CommonJS), Renderer (`src/renderer`), gemeinsame Typen der Brücke (`src/shared/bridge.ts`). Logik, die Tests braucht, kennt weder Electron noch DOM: Core-Verbindung, Brücke im Main und `TerminalController` im Renderer arbeiten gegen schmale Schnittstellen (`CorePort`, `BridgeWindow`, `TerminalSurface`).
- **Ein Electron-Main für alle Fenster.** `requestSingleInstanceLock`: Ein zweiter Start beendet sich und öffnet im laufenden Main ein neues Fenster. Der Main hält genau eine Verbindung zum Core für alle Fenster und verteilt Events an die Fenster, die eine View der Session haben. Ihm gehören alle Fenster, deshalb speichert er später auch das ganze Layout aller Fenster (#25 Persistenz im Core, #29 Wiederherstellung).
- **Core-Anbindung im Main:** zuerst verbinden; nur wenn die Pipe nicht existiert (`ENOENT`), den Core-Einstieg (`packages/core/dist/bin/termdock-core.js`) mit `process.execPath`, `ELECTRON_RUN_AS_NODE=1`, `detached`, `stdio: "ignore"` starten und mit wachsenden Wartezeiten (50 ms bis 1 s) bis 5 s Gesamtzeit erneut verbinden. Andere Fehler (`protocol_mismatch`, verweigerter Zugriff) gehen ohne Start an den Benutzer. Die erste Anfrage nach `hello` ist `core.status` mit 60 s Timeout, weil sie auf den Abgleich beim Start wartet (ADR 0001); `session.create` und `session.attach` haben ebenfalls 60 s (kalter WSL-Start, tmux-Snapshot), alle übrigen Anfragen 10 s. Ein `session.attach`, das erst nach seinem Timeout antwortet, wird sofort wieder gelöst. Ein zweiter Start während des Wartens wird vorgemerkt und öffnet sein Fenster, sobald die Verbindung steht. Schließt der Benutzer alle Fenster, endet nur die Verbindung, der Core läuft weiter.
- **Abhängigkeitsrichtung:** Der Main nutzt aus `@termdock/core` nur die Client-Bibliothek (`connect`, `defaultPipeName`, `IpcError`) und den Pfad des Core-Einstiegs. Renderer und Preload kennen nur Typen aus `@termdock/protocol`. Der Core kennt den Desktop nicht.
- **Brücke Renderer ↔ Main (ADR 0002):** Der Renderer erreicht weder Pipe noch Node noch Electron (`contextIsolation`, `sandbox`, kein `nodeIntegration`, CSP `script-src 'self'`, keine Navigation, keine neuen Fenster). Der Preload bietet `window.termdock` mit einer festen Liste von Aufrufen (`coreStatus`, `listSessions`, `createSession`, `attach`, `detach`, `input`, `resize`, `claimWriter`) über einen Kanal `termdock:call` und alle Events über `termdock:event`. Der Main prüft jede Nachricht zur Laufzeit, gibt Fehler als `{ code, message }` mit den stabilen Codes aus ADR 0002 zurück (plus `timeout`, `closed`) und lässt Aufrufe für eine View nur aus dem Fenster zu, das sie angehängt hat. Schließt ein Fenster, lädt sein Renderer neu (Navigation im Hauptframe) oder stürzt er ab (`render-process-gone`), löst er dessen Views (`session.detach`), damit keine tote View das Schreibrecht hält; ein `attach` der alten Seite, das danach antwortet, wird ebenfalls gelöst.
- **Ausgabe-Sequenz und Snapshot-Marke:** Der Main nummeriert `session.output` je Session (ab 1) und gibt jedem Ausgabe-Event seine Nummer mit. Die Antwort auf `attach` an den Renderer enthält `outputSeq`: die letzte Nummer, die der Main bis zur Verarbeitung der Core-Antwort gesehen hat. Der Core hält Events dieser Verbindung während des `attach` zurück, hängt die Ausgabe dieser Zeit an den Snapshot und sendet die zurückgehaltenen Events direkt hinter der Antwort; der Client verarbeitet sie im selben Durchlauf, also vor der Marke. Die View verwirft jede Ausgabe mit Nummer ≤ Marke, gepuffert oder später eintreffend. So erscheint keine Ausgabe doppelt, auch nicht bei einer zweiten View derselben Session im selben Fenster (#27). Grenze: Liefert die Pipe die zurückgehaltenen Events in einem späteren Lesevorgang als die Antwort, liegen sie über der Marke und erscheinen doppelt; exakt wäre eine Marke vom Core in der Attach-Antwort (Protokolländerung).
- **Terminal-View:** xterm.js mit Fit-Addon, ein `TerminalController` je View. Ablauf: abonnieren, `session.attach`, Terminal auf die Sitzungsgröße bringen, Snapshot schreiben, gepufferte und dann Live-Ausgabe schreiben. Nur der Schreiber sendet Eingabe und Größe; Leser verwerfen alles aus `onData`, auch automatische Antworten (ADR 0003). „Schreibrecht übernehmen“ sendet `session.claimWriter`; die Rolle folgt `view.writerChanged`, eine Ablehnung steht in der Statusleiste. Endet die Core-Verbindung, ist die Rolle `closed` endgültig: keine Rollenwechsel, keine Eingabe, keine Größe mehr. Scheitert `attach`, löst die View ihre Abos und verwirft gepufferte Ausgabe.
- **Lesende Views in Phase 2:** Ein Leser stellt das Terminal in der Größe des Schreibers dar. Ist seine Fläche kleiner, wird es beschnitten (`overflow: hidden`), nicht skaliert. Damit ist die offene Frage aus ADR 0003 („skaliert oder beschnitten“) entschieden. Die Fläche um den Bildschirm von xterm.js (`.xterm-screen`, nach dem Zeichnen gemessen) ist abgedunkelt, unten rechts steht „Größe des Schreibers: C×R“ (#27).
- **Split-Panes (#27):** Der Tab hält einen `PaneNode`-Baum mit 1 bis 4 Panes (`MAX_PANES_PER_TAB`) im Store; Teilen in gleicher Richtung fügt ein Geschwister ein, Schließen vereinfacht den Baum, Trenner ändern `sizes` mit Mindestanteil. Jedes Pane ist eine eigene View (`TerminalController`). Die Panes eines Tabs sind eine flache Liste absolut positionierter Elemente (Rechtecke aus dem Baum, `pane-layout.ts`) mit der Pane-ID als Schlüssel, damit ein Umbau des Baums keine View neu anhängt. Ein neues Pane zeigt dieselbe Session als weitere View (keine ungewollten langlebigen Sessions, `LayoutPane.sessionId` ist Pflicht); weil diese View liest, bleibt das geteilte, schreibende Pane aktiv und fokussiert. Umschalt+Klick in der Sidebar teilt mit der angeklickten Session, dann wird das neue Pane aktiv. Schließen führt gleichgerichtete Splits zusammen. Ein Drücken ins Pane macht es aktiv; erst ein Klick ohne Ziehen, ohne Doppelklick und ohne Auswahl im Terminal übernimmt bei einem Leser das Schreibrecht, Markieren von Text nicht. Fit und `session.resize` laufen nur im Schreiber und gebündelt: `layoutChanged` plant eine Anpassung nach 60 ms, weitere Änderungen in dieser Zeit fallen in dieselbe (höchstens etwa 16 je Sekunde beim Ziehen); `proposeSize` liefert ohne Fläche nichts. Das Fit-Addon liest die berechnete Höhe des Elternelements und zieht dessen Innenabstand nicht ab; `.terminal-view` hat deshalb `box-sizing: content-box`, sonst fehlt die letzte Zeile.
- **Snapshot ohne Cursor:** Protokoll 1.0 überträgt die Cursorposition des Snapshots nicht. Die View entfernt Leerzeilen am Ende des Snapshots, damit der Cursor hinter dem zuletzt geschriebenen Text steht (bei einer Shell der Prompt). Steuersequenzen, die der Core während der Aufnahme hinten anhängt (etwa tmux, das den Cursor ein- und ausschaltet), bleiben erhalten, nur ihre Zeilenumbrüche fallen weg. Für Vollbildprogramme stimmt der Cursor erst nach dem nächsten Neuzeichnen; ein Cursor im Protokoll ist ein eigener Change.
- **Sidebar, Tabs, Statusleiste (#26):** Der Zustand eines Fensters liegt in einem reinen Store (`ui-store.ts`) in der Form `LayoutWindow`/`LayoutTab` (seit #27 mit Pane-Baum); jedes Fenster hat eigene Tabs, ein Fenster ohne Tabs zeigt Sidebar und Leerzustand, eine Session wird nicht mehr automatisch geöffnet. Alle Tabs eines Fensters bleiben angehängt und werden nur versteckt (`visibility: hidden`, gleiche Fläche): Ein Tabwechsel ändert nichts am Core, die Ausgabe läuft weiter, und kein verstecktes Terminal sendet eine falsche Größe. Schließen eines Tabs löst die View (`session.detach`). Weil der Core kein Event für neue Sessions kennt, sendet der Main nach jedem erfolgreichen `createSession` `sessionCreated` an alle Fenster; Zustandswechsel gehen schon an alle. Ein Tab einer Session, die weder `Running` noch `Detached` ist, hängt nicht an, sondern nennt den Zustand (ADR 0005). Workspaces erscheinen als Gruppen nach `workspaceId` (Überschrift ist die ID), bis Phase 3 Namen liefert.
- **Screenshot-Modus** (`--screenshot <dir>`): Die App startet einen eigenen Core mit eigener Pipe (`TERMDOCK_PIPE`), Datenbank in einem Temp-Verzeichnis (`TERMDOCK_DATA_DIR`) und tmux-Socket `termdock-test` (`TERMDOCK_TMUX_SOCKET`), nutzt ein eigenes Electron-Profil im Temp-Verzeichnis und keine Einzelinstanz-Sperre. Sie legt fünf Sessions an, bringt sie in die Zustände `Running`, `Detached`, `Exited` (`exit`) und `Interrupted` (`tmux kill-session` über `wsl.exe` auf dem Test-Socket), öffnet sie per Klick im Renderer als Tabs, speichert die Fenster (Sidebar, eingeklappte Sidebar, leeres Fenster mit Formular, Hinweis-Tab, Leser; seit #27 in einem dritten Fenster dieselbe Session in zwei Panes mit beschnittenem Leser, `stty size` vor und nach dem Ziehen eines Trenners mit echten Mausereignissen über `webContents.sendInputEvent`, 3 und 4 Panes, `vim` vor und nach Teilen und Ziehen samt Prüfung der Cursorposition gegen tmux) per `webContents.capturePage()` als PNG und beendet danach mit `core.shutdown { stopSessions: true }` alle Sessions und den Core. Scheitert schon das Verbinden oder die erste Antwort, beendet sie den gestarteten Core ebenso, notfalls über seine Prozess-ID, und wartet auf sein Ende, bevor sie das Datenverzeichnis entfernt. Der Produktiv-Socket `termdock` wird nie berührt.

## Folgen

- Jede Erweiterung der Brücke braucht eine Prüfung im Main (`coreStatus` und `sessionCreated` aus #26 haben sie).
- Je Pane ein `TerminalController` (#27); die Brücke verteilt Events je Fenster und Session, zwei Views derselben Session im selben Fenster trennt die Sequenzmarke (Restlücke #34).
- `npm ci` lädt das Electron-Binary; Tests und Typecheck brauchen es nicht.
- Electron lädt beim Import von `@termdock/core` auch node-pty und `node:sqlite`; beides läuft unter Electron 45 (ADR 0003, 0004). Ein Unterpfad-Export nur für den Client würde das vermeiden.
- Ein Absturz des Core trennt alle Fenster; sie zeigen „Verbindung zum Core getrennt“. Automatisches Wiederverbinden ist noch nicht umgesetzt.
