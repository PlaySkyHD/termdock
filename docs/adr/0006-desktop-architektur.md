# ADR 0006: Desktop-Architektur

Status: angenommen (13.11.2026)

## Kontext

Phase 2 (Kapitel 12) bringt die Oberfläche: Sidebar, Tabs, 2–4 Split-Panes, Tastenkürzel und Layout-Wiederherstellung. Fenster sind Clients des Core (ADR 0001) und sprechen nur über die Pipe mit ihm (ADR 0002). Der PoC aus Phase 0 (`poc/`) hat Electron 45.3.1 mit xterm.js 6.0.0, `contextIsolation`, `sandbox` und CSP geprüft. Die Struktur muss #26 (Sidebar/Tabs), #27 (Splits), #28 (Keymap) und #29 (Layout-Wiederherstellung) tragen, ohne dass dieses Gerüst ihre Funktionen vorwegnimmt.

## Entscheidung

- **Stack:** Electron 45.3.1 (wie im PoC), React und TypeScript, ohne UI-Bibliothek. Eigenes CSS im Stil von VS Code (Dark+). Der Renderer wird mit Vite gebaut (`dist/renderer`, relative Pfade, kein Inline-Skript), Main und Preload mit `tsc -b`. Paket `apps/desktop`, Start mit `npm start -w apps/desktop`.
- **Aufteilung:** Main (`src/main`), Preload (`src/preload`, CommonJS), Renderer (`src/renderer`), gemeinsame Typen der Brücke (`src/shared/bridge.ts`). Logik, die Tests braucht, kennt weder Electron noch DOM: Core-Verbindung, Brücke im Main und `TerminalController` im Renderer arbeiten gegen schmale Schnittstellen (`CorePort`, `BridgeWindow`, `TerminalSurface`).
- **Ein Electron-Main für alle Fenster.** `requestSingleInstanceLock`: Ein zweiter Start beendet sich und öffnet im laufenden Main ein neues Fenster. Der Main hält genau eine Verbindung zum Core für alle Fenster und verteilt Events an die Fenster, die eine View der Session haben. Ihm gehören alle Fenster, deshalb speichert er später auch das ganze Layout aller Fenster (#25 Persistenz im Core, #29 Wiederherstellung).
- **Core-Anbindung im Main:** zuerst verbinden; nur wenn die Pipe nicht existiert (`ENOENT`), den Core-Einstieg (`packages/core/dist/bin/termdock-core.js`, im installierten Paket unter `resources/app.asar.unpacked`, ADR 0007) mit `process.execPath`, `ELECTRON_RUN_AS_NODE=1`, `detached`, `stdio: "ignore"` starten und mit wachsenden Wartezeiten (50 ms bis 1 s) bis 5 s Gesamtzeit erneut verbinden. Andere Fehler (`protocol_mismatch`, verweigerter Zugriff) gehen ohne Start an den Benutzer. Die erste Anfrage nach `hello` ist `core.status` mit 60 s Timeout, weil sie auf den Abgleich beim Start wartet (ADR 0001); `session.create` und `session.attach` haben ebenfalls 60 s (kalter WSL-Start, tmux-Snapshot), alle übrigen Anfragen 10 s. Ein `session.attach`, das erst nach seinem Timeout antwortet, wird sofort wieder gelöst. Ein zweiter Start während des Wartens wird vorgemerkt und öffnet sein Fenster, sobald die Verbindung steht. Schließt der Benutzer alle Fenster, endet nur die Verbindung, der Core läuft weiter.
- **Neustart des Core (#130):** Die Verbindung hält ein Supervisor (`core-supervisor.ts`, ohne Electron, Uhr, Wartefunktion und `connect` eingespeist) mit den Zuständen `connecting`, `connected`, `restarting`, `failed`, `stopped`. Endet die Verbindung, während die App läuft, ruft er erneut `connectOrStartCore` (gleiche Wartezeiten; läuft schon ein anderer Core, verbindet er sich nur), höchstens 3 Neustarts in 2 Minuten, gescheiterte eingeschlossen (1 s Pause dazwischen); danach `failed`, bis „Core neu starten“ (Brückenaufruf `restartCore`) den Zähler leert. Sobald das Beenden feststeht (`retainAll` des `QuitFlow`, auch bei `session-end`, `window-all-closed`, Ende des Screenshot-Laufs), setzt der Main ihn auf `stopped`, also vor Speichern und `core.shutdown`. Der Supervisor bietet eine `CorePort`, die über Neustarts dasselbe Objekt bleibt und Abos an jede neue Verbindung weitergibt; Brücke, Koordinator und Schließen-Ablauf behalten so ihre. Beim Ende der Verbindung vergisst die Brücke alle Views und Sequenznummern und sendet `coreClosed { restarting }`, nach dem Erfolg `coreRestarted`, nach dem Aufgeben `coreClosed { restarting: false }`. Der Renderer zeigt im Pane „Core startet neu …“ bzw. „Verbindung zum Core getrennt“ mit „Core neu starten“ (auch in der Statusleiste); die alte View sendet nichts mehr, Eingaben gehen verloren. Nach `coreRestarted` holt `connectStore` Sessions, Workspaces und Status neu, `UiStore.coreRestarted` setzt die Liste und erhöht `coreGeneration` in einem Schritt, und `PaneTree` hängt jedes `PaneView` mit der Generation als Schlüssel neu ein (das Pane-Element behält seinen). Eine Session, die der Abgleich `Interrupted` markiert, zeigt so wieder ihren Platzhalter. Nur ein Pane, das der Neustart neu einhängt (`claimsAfterRestart`: zuletzt mit älterer Generation gezeichnet), übernimmt als aktives Pane des Fensters mit dem Fokus (`document.hasFocus()`) nach dem Anhängen das Schreibrecht (`claimOnOpen`, einmal je Einhängen gelesen); der Core gibt es atomar weiter, also schreibt genau eine View je Session, und später geöffnete Panes hängen wie sonst an. Ein Fenster, das während der Trennung lädt, fragt beim Start `coreConnection` (gilt nur, solange kein neueres Event kam); Events vor der neuen Liste hält `connectStore` wie beim Start zurück und wendet sie danach an. Der Knopf meldet den Neustart mit `coreClosed { restarting: true }`. Beendet der Nutzer mit „Sessions beenden“, während ein Neustart verbindet, bekommt der neue Core danach ebenfalls `core.shutdown { stopSessions: true }`; `close` wartet darauf höchstens 5 s. „Core neu gestartet“ steht 4 s oben im Tab-Bereich. Den Grund des Absturzes nennt bis #129 nur `console.error`.
- **Abhängigkeitsrichtung:** Der Main nutzt aus `@termdock/core` nur die Client-Bibliothek (`connect`, `defaultPipeName`, `IpcError`) und den Pfad des Core-Einstiegs. Renderer und Preload kennen nur Typen aus `@termdock/protocol`. Der Core kennt den Desktop nicht.
- **Brücke Renderer ↔ Main (ADR 0002):** Der Renderer erreicht weder Pipe noch Node noch Electron (`contextIsolation`, `sandbox`, kein `nodeIntegration`, CSP `script-src 'self'`, keine Navigation, keine neuen Fenster). Der Preload bietet `window.termdock` mit einer festen Liste von Aufrufen (`coreStatus`, `listSessions`, `createSession`, `attach`, `detach`, `input`, `resize`, `claimWriter`, seit #63 auch die Verwaltung von Workspaces, Projekten und Sessions, seit #64 Einstellungen, Startprofile und WSL-Distributionen) über einen Kanal `termdock:call` und alle Events über `termdock:event`. Der Main prüft jede Nachricht zur Laufzeit, gibt Fehler als `{ code, message }` mit den stabilen Codes aus ADR 0002 zurück (plus `timeout`, `closed`) und lässt Aufrufe für eine View nur aus dem Fenster zu, das sie angehängt hat. Schließt ein Fenster, lädt sein Renderer neu (Navigation im Hauptframe) oder stürzt er ab (`render-process-gone`), löst er dessen Views (`session.detach`), damit keine tote View das Schreibrecht hält; ein `attach` der alten Seite, das danach antwortet, wird ebenfalls gelöst.
- **Ausgabe-Sequenz und Snapshot-Marke (#34):** Der Core nummeriert die Ausgabe jeder Session (`session.output { seq }`) und liefert in der Attach-Antwort die Marke `outputSeq`: die Nummer der letzten Ausgabe, die nicht an die neue View ging (Protokoll 1.1, ADR 0003). Der Main gibt jedem Ausgabe-Event diese Nummer mit und reicht die Marke an den Renderer weiter. Die View verwirft jede Ausgabe mit Nummer ≤ Marke, gepuffert oder später eintreffend. Die Grenze ist exakt, auch für Events, die der Core während des `attach` zurückhält und die erst in einem späteren Lesevorgang ankommen, und bei einer zweiten View derselben Session im selben Fenster (#27). Ein Core mit Protokoll 1.0 sendet weder `seq` noch `outputSeq`; dann zählt der Main wie zuvor selbst und nimmt als Marke die letzte Nummer, die er bis zur Verarbeitung der Antwort gesehen hat (mit der alten Grenze für spät gelesene Events).
- **Terminal-View:** xterm.js mit Fit-Addon, ein `TerminalController` je View. Ablauf: abonnieren, `session.attach`, Terminal auf die Sitzungsgröße bringen, Snapshot schreiben, gepufferte und dann Live-Ausgabe schreiben. Nur der Schreiber sendet Eingabe und Größe; Leser verwerfen alles aus `onData`, auch automatische Antworten (ADR 0003). „Eingabe übernehmen“ (Knopf im lesenden Pane und in der Statusleiste) oder ein Doppelklick ins lesende Pane sendet `session.claimWriter`; die Rolle folgt `view.writerChanged`, eine Ablehnung steht in der Statusleiste. Endet die Core-Verbindung, ist die Rolle `closed` endgültig: keine Rollenwechsel, keine Eingabe, keine Größe mehr. Scheitert `attach`, löst die View ihre Abos und verwirft gepufferte Ausgabe.
- **Lesende Views (#27, Zoom seit #66):** Ein Leser stellt das Terminal im Raster des Schreibers dar und verkleinert seine Schrift, bis es in seine Fläche passt (Variante A, ADR 0003): `readerFontSize` (`terminal-size.ts`, rein) rechnet aus Raster, Fläche und Zellgröße bei normaler Schrift die größte ganze Schriftgröße bis 14 px, mindestens 8 px; darunter wird beschnitten (`overflow: hidden`). Der `TerminalController` wendet sie über `TerminalSurface.setFontSize` an, nach jedem Rollen- oder Größenwechsel und gebündelt nach `layoutChanged`, und geht pixelweise kleiner, solange das Raster mit der gerenderten Zellgröße noch nicht passt; ein Schreiber setzt vor dem Fit die normale Schrift. Die Zellgröße bei normaler Schrift liest `TerminalView` aus den Render-Abmessungen von xterm.js (wie das Fit-Addon) nur, solange die normale Schrift gilt, damit Rundung keine Schwingung erzeugt. Die Fläche um den Bildschirm von xterm.js (`.xterm-screen`, nach dem Zeichnen gemessen) ist abgedunkelt, unten rechts stehen „Größe des Schreibers: C×R“ und der Knopf „Eingabe übernehmen“.
- **Split-Panes (#27):** Der Tab hält einen `PaneNode`-Baum mit 1 bis 4 Panes (`MAX_PANES_PER_TAB`) im Store; Teilen in gleicher Richtung fügt ein Geschwister ein, Schließen vereinfacht den Baum, Trenner ändern `sizes` mit Mindestanteil. Jedes Pane ist eine eigene View (`TerminalController`). Die Panes eines Tabs (seit #67 aller Tabs des Fensters) sind eine flache Liste absolut positionierter Elemente (Rechtecke aus dem Baum, `pane-layout.ts`) mit der Pane-ID als Schlüssel, damit ein Umbau des Baums keine View neu anhängt. Teilen per Kürzel oder Knopf startet seit #66 eine neue Session (`splitActivePane` in `commands.ts`, `session.create` mit Backend, Distribution, Shell, `launch.cwd` und Workspace der Session des aktiven Panes, ohne `command`, `env` und `profileId`; Name `<Name> N` mit der kleinsten freien Nummer); das neue Pane wird aktiv und schreibt, jedes Pane hat eigene Shell und Größe. Vorher zeigte ein neues Pane dieselbe Session lesend, was im Test als „vier Panes, eine Eingabe“ verwirrte. Das aktuelle Verzeichnis der Shell kennt das Protokoll nicht; ein Teilen, das nach dem Anlegen kein Pane mehr findet, öffnet die Session in einem eigenen Tab. Dieselbe Session in einem zweiten Pane gibt es nur ausdrücklich per Umschalt+Klick in der Sidebar; weil diese View liest, bleibt das geteilte, schreibende Pane aktiv und fokussiert. Umschalt+Klick mit einer anderen Session macht das neue Pane aktiv. Schließen führt gleichgerichtete Splits zusammen. Ein Drücken ins Pane macht es aktiv und ändert sonst nichts; nur ein Doppelklick ohne Ziehen in einen Leser (`takesInput` in `pane-layout.ts`) oder der Knopf „Eingabe übernehmen“ übernimmt das Schreibrecht. So springen Schreiber und Größe beim Klicken nicht mehr (#66). Fit und `session.resize` laufen nur im Schreiber und gebündelt: `layoutChanged` plant eine Anpassung nach 60 ms, weitere Änderungen in dieser Zeit fallen in dieselbe (höchstens etwa 16 je Sekunde beim Ziehen); `proposeSize` liefert ohne Fläche nichts. Das Fit-Addon liest die berechnete Höhe des Elternelements und zieht dessen Innenabstand nicht ab; `.terminal-view` hat deshalb `box-sizing: content-box`, sonst fehlt die letzte Zeile.
- **Snapshot ohne Cursor:** Das Protokoll überträgt die Cursorposition des Snapshots nicht. Die View entfernt Leerzeilen am Ende des Snapshots, damit der Cursor hinter dem zuletzt geschriebenen Text steht (bei einer Shell der Prompt). Steuersequenzen, die der Core während der Aufnahme hinten anhängt (etwa tmux, das den Cursor ein- und ausschaltet), bleiben erhalten, nur ihre Zeilenumbrüche fallen weg. Für Vollbildprogramme stimmt der Cursor erst nach dem nächsten Neuzeichnen; ein Cursor im Protokoll ist ein eigener Change.
- **Sidebar, Tabs, Statusleiste (#26):** Der Zustand eines Fensters liegt in einem reinen Store (`ui-store.ts`) in der Form `LayoutWindow`/`LayoutTab` (seit #27 mit Pane-Baum); jedes Fenster hat eigene Tabs, ein Fenster ohne Tabs zeigt Sidebar und Leerzustand, eine Session wird nicht mehr automatisch geöffnet. Alle Tabs eines Fensters bleiben angehängt und werden nur versteckt (`visibility: hidden`, gleiche Fläche): Ein Tabwechsel ändert nichts am Core, die Ausgabe läuft weiter, und kein verstecktes Terminal sendet eine falsche Größe. Schließen eines Tabs löst die View (`session.detach`). Neue Sessions meldet der Core mit `session.created` (Protokoll 1.2, #46, ADR 0002); der Main leitet es als `sessionCreated` an alle Fenster weiter, auch für Sessions anderer Clients, und meldet nach `createSession` selbst nichts. Der Store ist idempotent (Event, Antwort und `session.list` dürfen alle dieselbe Session melden); Zustandswechsel gehen ebenfalls an alle. Ein Tab einer Session, die weder `Running` noch `Detached` ist, hängt nicht an, sondern nennt den Zustand (ADR 0005). Workspaces und Archiv: siehe „Sidebar mit Workspaces“ (#63).
- **Sidebar mit Workspaces (#63):** Die Sidebar zeigt die Workspaces des Core (`workspace.list`, Reihenfolge des Core) mit Namen, Projekten und Sessions, darunter „Ohne Gruppe“ (auch Sessions, deren Workspace das Fenster nicht kennt) und das eingeklappte Archiv. Die Brücke bekommt zehn Aufrufe (`listWorkspaces`, `create|update|deleteWorkspace`, `create|update|deleteProject`, `updateSession`, `archiveSession`, `deleteSession`; der Main prüft Typen und nicht leere IDs, der Core den Rest) und drei Events an alle Fenster, auch für Änderungen anderer Clients: `workspaceChanged` (ganze Liste), `sessionUpdated`, `sessionRemoved` (der Main vergisst die Sequenznummer). Der Store übernimmt aus `sessionUpdated` nur Name, Workspace, Logging und `updatedAt`, nie den Zustand (er gehört `stateChanged`); `connectStore` hält die Events vor der ersten Liste zurück, und ein `workspaceChanged` gewinnt gegen eine spätere Antwort von `listWorkspaces` (er enthält die ganze Liste und ist nie älter als das, was danach eintrifft). Eine gelöschte Session verschwindet aus dem Store; ihre Tabs zeigen den Platzhalter „Session nicht gefunden“. Die Regeln, wohin eine Session darf (`canDrop`: nicht in den eigenen Workspace, gruppenlos nur aus einem Workspace, Archiv für jede lebende Session, eine archivierte Session nirgends), und die Einträge der Kontextmenüs stehen einmal in `sidebar-model.ts` (rein), damit Maus und Tastatur nicht auseinanderlaufen. Löschen (Workspace, Projekt, Session) und Archivieren, auch per Drag&Drop, fragen vorher in einem modalen Dialog (Standard „Abbrechen“, Fokusfalle, Esc bricht ab); Anlegen und Umbenennen nutzen einen kleinen Dialog, ein Fehler des Core bleibt im Dialog. Der Store ändert sich erst über die Events des Core, nicht vorab.
- **Drag&Drop (#63, `renderer/drag/`):** Zeigerereignisse statt HTML5-Ziehen, das eine Schleife des Betriebssystems fährt, sich nicht mit `sendInputEvent` prüfen lässt und keine Abbruchtaste hat. `drag-model.ts` (rein) ist die Zustandsmaschine `idle`, `pressed`, `dragging`, `aborted` mit Schwelle von 5 Pixeln und der Nutzlast `{ kind, id, label }` (`session`, `tab`, `pane`); `drag-controller.ts` hängt `pointermove`, `pointerup`, `pointercancel`, `keydown` (Esc) und `blur` des Fensters an, fragt eine eingespeiste Trefferfunktion und unterdrückt den `click` nach einem Ziehen; `DragProvider.tsx` ist der React-Kontext (`sourceProps`, `targetClass`, Schatten am Zeiger). Ziele sind Elemente mit `data-drop-target`; jedes gültige Ziel ist beim Ziehen gestrichelt umrahmt, das Ziel unter dem Zeiger voll. Das Ziel wird beim Loslassen erneut geprüft. Das Kontextmenü (`ContextMenu.tsx`, `menu-navigation.ts`) öffnet per Rechtsklick, Menütaste oder Umschalt+F10 und bietet dieselben Aktionen.
- **Tabs und Panes anordnen (#67):** Ein `DragProvider` je Fenster (`App.tsx`) trägt Sidebar, Tab-Leiste und Panes; jeder Bereich meldet seine Regeln mit `useDropHandler`, ein Ziel gehört dem ersten, der es annimmt. Zonen-Ziele (`drag/drop-zones.ts`): Ein Element mit `data-drop-zones="pane"` steht für `<id>:left|right|top|bottom|center` (Kanten sind die äußeren 30 %, Grenzen die Diagonalen; eine gesperrte Kante fällt auf die Mitte zurück), mit `"sides"` für die Hälften eines Tabs. Die Regeln stehen einmal in `layout-moves.ts` (rein, `applyMove`): Tab umsortieren, Tab, Pane oder Sidebar-Session auf eine Zone (Kante teilt, Mitte ersetzt die View), Pane auf die Tab-Leiste, höchstens 4 Panes und 64 Tabs, ein leerer Tab schließt, die verschobene View wird aktiv. Die Baumfunktionen dafür (`pane-tree.ts`) nutzt auch der Store. Kontextmenüs an Tab, Griff des Panes und Session (`layout-menus.ts`) und `Ctrl+Shift+PageUp`/`PageDown` sind dieselben Züge. Damit ein Pane beim Verschieben seine View behält (der Core gibt das Schreibrecht nur der ersten View und kennt keinen Nachfolger, ADR 0005), zeichnet das Fenster die Panes aller Tabs in einer flachen Liste (`.pane-tree`, Schlüssel Pane-ID, `layoutWindow` in `pane-layout.ts`); Panes versteckter Tabs sind `visibility: hidden` und tragen `data-tab-active="false"`.
- **Layout-Vorschläge beim Ziehen (#78):** Ein Tab oder Pane, das 250 ms am oberen Rand des Tab-Bereichs (32 Pixel) verweilt, öffnet die Muster-Leiste (`SnapBar.tsx`) mit „2 nebeneinander“, „2 übereinander“, „1 + 2“, „2 + 1“ und „2 × 2“; sichtbar sind nur Muster mit einem gültigen Feld (`visiblePatterns`). Streifen und offene Leiste reichen nur über die Breite der Leiste und 16 Pixel daneben (`snapBarStep`); offen bleibt sie vom oberen Rand bis zu ihrer Unterkante, darunter gelten sofort wieder die Zonen der Panes. Jede Bewegung über 4 Pixel startet die Wartezeit neu (`dwellAnchor`), also öffnet ein Überqueren oder Bewegen im Rand sie nicht. Die Leiste ist eine Zeile so breit wie ihre Muster (höchstens 130 Pixel hoch) und bricht nur in zu schmalen Fenstern um; versteckt ist sie `visibility: hidden`, damit ihre Box für den Streifen messbar bleibt. Jedes Feld ist ein Ziel `snap:<muster>:<feld>` mit Namen und Statuspunkt der View, die dort landen würde. Die Leiste bleibt versteckt eingehängt, weil die gültigen Ziele beim Start des Ziehens feststehen. Die Regel ist ein weiterer Zug von `applyMove` (`snap-layouts.ts`, rein): Der aktive Tab wird geordnet, die gezogene View kommt ins Feld, die übrigen folgen in Baumreihenfolge, ein anderer Tab geht im aktiven auf. Leere Felder werden nicht angelegt, weil ein `LayoutPane` immer eine Session zeigt. Panes behalten ihre IDs und damit View, Rolle und Eingabe-Lock. Die Menüs von Tab und Pane-Griff bieten dieselben Muster (Element ins erste Feld). Die Screenshot-Szenen (`main/screenshot-snap.ts`) ziehen mit echten Mausereignissen und prüfen Views, Rollen und Geometrie.
- **Ziehen zwischen Fenstern (#68):** Chromium gibt dem Fenster, in dem die Maustaste gedrückt wurde, die Zeigerereignisse auch außerhalb seiner Fläche; der `DragController` läuft deshalb weiter, `drag-model.ts` markiert den Zug mit `outside`, und ein Loslassen außerhalb wird für Tabs und Panes (`leaves`) zum Effekt `outside`. Der Main koordiniert (`main/window-transfer.ts`, `WindowTransfers`, ohne Electron hinter `TransferHost`): Er rechnet Client-Koordinaten über `getContentBounds()` in Bildschirmkoordinaten um, nimmt das zuletzt fokussierte Fenster unter dem Punkt (`windowAtPoint`, Electron kennt keine Z-Ordnung) und meldet ihm `transferHover`; dessen `DragProvider` zeigt Ziele, Zonen und Schatten wie bei einem eigenen Zug (äußerer Modus, Nutzlast `incoming`; ein eigener Zug hat Vorrang). Brücke: `transferHover`, `transferHoverEnd`, `transferDrop { item, at, whole }` und `transferAttached { transferId, views? }`, Events `transferHover`, `transferIn`, `transferCancel`, `transferOut`; der Main prüft das Element wie ein Layout (`validateLayoutDocument`) und nimmt nur Views des aufrufenden Fensters. Ablegen über einem anderen Fenster sendet ihm `transferIn` mit dem Punkt; außerhalb aller Fenster öffnet der Main ein Fenster mit der Tab-Leiste unter dem Zeiger (`boundsAtPointer`: Titelleiste aus `getBounds` − `getContentBounds`, geklemmt auf die Arbeitsfläche des Bildschirms unter dem Zeiger, `screen.getDisplayNearestPoint`; ebenso ein wanderndes Fenster) und sendet `transferIn` ohne Punkt, sobald dessen Seite `windowLayout` gefragt hat (die Seite abonniert die Events vorher, `TransferInbox` hält sie bis zu den Zielen); ist das Element der ganze Inhalt seines Fensters, wandert stattdessen das Fenster. Das Ziel setzt das Element mit neuen IDs ein (`applyIncoming` über `applyMove`, ohne Layout-Vorschläge und ohne die Mitte eines Panes: sie ersetzte eine View des Ziels, bevor die Übergabe feststeht, und ein Abbruch brächte sie nicht zurück), hängt seine Panes an (sie lesen, solange die alten Views da sind) und meldet nach dem letzten Pane (`IncomingMoves`, `settleIncoming`; ein Platzhalter zählt sofort) die neue View je Quell-Pane. Der Main überträgt dann jedem alten Schreiber das Recht mit `session.claimWriter` an seinen Nachfolger (die Brücke kennt den Schreiber aus `view.writerChanged` und der Attach-Antwort; ein Event, das während des Anhängens kam, schlägt die Antwort) und lässt erst danach die Quelle das Element entfernen (`transferOut`) oder schließt sie, wenn ihr zuletzt gemeldetes Layout nichts anderes hält (`holdsOnly`; nicht das letzte Fenster, also kein Schließen-Dialog; sie verlässt das Layout). Die Quelle baut das Element einmal je Zug und meldet das Überfahren höchstens einmal je Frame (`OutgoingMoves`); ein Pane, das vor dem Anhängen verschwindet, meldet sich als gescheitert, damit die Übergabe nicht bis zum Zeitlimit hängt. So sieht der Core je View ein `session.attach` und ein `session.detach`, nie zwei Schreiber und keinen Moment ohne. Lehnt das Ziel ab, fehlt ein Nachfolger, scheitert ein `claimWriter` (übertragene Rechte holt der Main zurück), schließt ein Fenster oder vergehen 75 s, nimmt das Ziel seine Panes wieder heraus (`transferCancel`), und die Quelle behält alles. Das Ziel nennt jedes Quell-Pane; ohne View nur ein Platzhalter einer Session in einem Endzustand (`Exited`, `Interrupted`, `Archived`; `Interrupted` verlässt nur „Neu starten“, ADR 0005) oder einer fehlenden (`settlesWithoutView`). `Starting` wartet auf das Anhängen oder das Zeitlimit, denn dort läuft gleich ein Prozess, und der Core behält Views und Schreiber (#164). Für eine schreibende Quell-View prüft der Main eine solche Antwort beim Core (`session.list`) und bricht ab, wenn die Session nicht in einem Endzustand oder weg ist; sonst überträgt er nichts, und die Quelle löst ihre View trotzdem. Kennt die Brücke eine View der Quelle nicht mehr (Core-Neustart, archivierte Session) oder zeigt ein Nachfolger eine andere Session als sein Quell-Pane, bricht der Main ab; endet die Core-Verbindung, bricht er alle Übergaben ab (`coreClosed`). Während der Übergabe bleibt sie beim Main bekannt: Schließt oder lädt ein beteiligtes Fenster neu oder endet die Core-Verbindung zwischen zwei Schritten, bricht sie beim nächsten ab und gibt übertragene Schreibrechte zurück. Bekannte Grenze: Übernimmt ein drittes Fenster („Eingabe übernehmen“) das Schreibrecht, während der Main die Nachfolger prüft und überträgt, kann sein `claimWriter` es ihm wieder abnehmen oder die Übergabe einen Leser statt des Schreibers sehen; die Rolle hängt dann an der Reihenfolge der Aufrufe beim Core, es entstehen aber nie zwei Schreiber. Kein Protokollwechsel.
- **Layout-Wiederherstellung (#29):** Der Renderer meldet nach jeder Änderung den Teil seines `LayoutWindow` (Tabs, aktiver Tab, Sidebar; ohne `id`, `bounds`, `maximized`) über `reportLayout`; der Main hält je Fenster Teil und Geometrie im `LayoutCoordinator`, bündelt sie zu einem `LayoutDocument` und speichert mit `layout.save` (400 ms nach der letzten Änderung, höchstens 2 s nach der ersten, ein Speichern gleichzeitig, beim Beenden sofort mit 3 s Obergrenze). Jede Meldung prüft der Main als Gesamtdokument mit `validateLayoutDocument` (Grenzen, eindeutige IDs über Fenster); eine Verletzung ergibt `bad_request`. Position, Größe und Maximierung liest nur der Main (`getNormalBounds`). Bei `invalid_state` lädt er mit `layout.get` die Revision und speichert seinen Stand erneut (höchstens 3 Versuche; der letzte Stand gewinnt). Das letzte offene Fenster und alle Fenster beim Beenden bleiben im Layout, ein weiteres vom Benutzer geschlossenes Fenster wird entfernt. Beim Start öffnet der Main die Fenster des gespeicherten Layouts, Bounds geprüft gegen `screen.getAllDisplays()` (`fitBounds`: mindestens 200×100 Pixel sichtbar, sonst zentriert auf dem primären Bildschirm), höchstens 16 Fenster (Fenster, die im Layout bleiben, mitgezählt). Scheitert `layout.get`, wiederholt der Main es zweimal (300 ms, 1 s); danach speichert er nichts, solange kein `layout.get` geantwortet hat, und nie über ein gespeichertes Layout, das er nicht geladen hat. Beenden über `app.quit()` hält `before-quit` einmal an, behält alle Fenster im Layout, speichert (3 s Obergrenze), schließt die Verbindung und beendet dann; `session-end` (Windows-Abmeldung) behandelt er wie Beenden. Der Renderer bündelt seine Meldungen (50 ms, immer der letzte Stand; `pagehide` sendet sofort), und scheitert die erste Session-Liste, wiederholt er sie (1, 3, 8 s) und gilt danach als geladen, damit Panes den Platzhalter mit „Pane schließen“ zeigen. Der Renderer holt sein Fenster mit `windowLayout` (auch nach einem Neuladen) und meldet erst danach. Ein Pane mit einer Session in `Starting`, `Exited`, `Interrupted`, `Archived` oder ohne Session im Core zeigt einen Platzhalter mit Zustand, letztem Exit-Code und „Pane schließen“ (`paneContent`); eine fehlende Session gilt erst nach der ersten Session-Liste als fehlend. Endet die Session einer schon angehängten View, bleibt die View mit der letzten Ausgabe; oben im Pane zeigt eine Leiste Zustand und Grund (`restartBar`), in der schreibenden View mit „Neu starten“ (`restartSession`), in einer lesenden nur einen Hinweis. Der Core behält beim Neustart Views und Schreiber, also zeigt dieselbe View den neuen Lauf; eine Ablehnung steht in der Leiste, bis die Session wieder lebt oder neu geklickt wird (#164).
- **Schließen-Dialog (#60):** Beim Beenden durch den Benutzer (`before-quit`, Schließen des letzten Fensters) zählt der Main mit `session.list` die Sessions in `Running` oder `Detached` und liest `settings.get`; `planQuit` (rein, `shared/quit-decision.ts`) entscheidet: ohne laufende Session und bei `session-end` nie fragen und Sessions behalten, bei `confirmQuitWhileRunning: false` die gespeicherte `quitAction`, sonst Dialog. Der Dialog ist eine Ansicht des fokussierten Fensters (Event `quitRequested`, Aufruf `answerQuit`; `QuitPrompt` hält eine offene Frage, nur das gefragte Fenster antwortet, ein verschwundenes Fenster heißt „Abbrechen“). „Sessions beenden“ sendet nach dem Speichern des Layouts `core.shutdown { stopSessions: true }`; „Nicht mehr fragen“ speichert `confirmQuitWhileRunning: false` und `quitAction` per `settings.set`. Antwortet der Core nicht, beendet die App wie bisher und behält die Sessions.
- **Update-Dialog (#136):** Ein vom Main geladenes Update (ADR 0007) meldet die Brücke allen Fenstern mit `updateChanged { version? }`; ein Fenster, das später lädt, fragt einmal `updateState` (ein Event gewinnt gegen eine spätere Antwort, `nextUpdateOffer`). `UpdateDialog.tsx` steht unten rechts über der Statusleiste, ist nicht modal (`aria-modal="false"`, keine Fokusfalle) und nimmt beim Erscheinen nicht den Fokus, weil der Download zu einem beliebigen Moment endet und Tasten im Terminal bleiben müssen; Escape im Dialog heißt „Später“. Der Satz zu den Sessions (`updateSessionsNote`) zählt die laufenden Windows-Shells des Stores mit `countActiveWindows` (dieselbe Regel wie im Schließen-Dialog). `answerUpdate { choice: "install" | "later" }` prüft der Main; ohne angebotenes Update `not_found`. Die Antwort gilt für alle Fenster. Im Einstellungsdialog steht unter „Allgemein“ der Schalter „Nach Updates suchen“ (`checkForUpdates`).
- **Explorer-Panel (#202, ADR 0009):** Rechts neben dem Pane-Bereich (`.main__body`, `ExplorerPanel.tsx`) zeigt ein Panel das aktuelle Verzeichnis der Session, der es folgt: das aktive Pane, wenn es schreibt, sonst ein schreibendes Pane des aktiven Tabs, sonst das aktive Pane (`explorer-source.ts`, Rolle aus dem Status der View). Das Verzeichnis kommt aus dem Store: WSL vom Core (`cwdChanged`, #199), Windows aus der View (`relayCwd` in `session-cwd.ts` schreibt `TerminalController.onCwd` per `sessionCwdChanged` in den Store, #200). Die View bleibt über einen Neustart (#164) und meldet nur einen anderen Pfad; endet ein Lauf, lässt `relayCwd` sie deshalb ihren Pfad vergessen (`forgetCwd`), und ein Bericht, der kam, bevor der Store den neuen Lauf als live kannte, wird danach übernommen. Eine WSL-Session ohne Distro im Store (der Core meldet `session.created` vor dem Festlegen) nutzt die Standard-Distro aus `wsl.distros`, nur gefragt, wenn das Panel sie braucht (`needsDefaultDistro`, ein `wsl.exe`-Aufruf im Core); eine Antwort mit Namen gilt je Core-Generation, ohne Namen oder bei einem Fehler fragt das Fenster nach wachsender Pause (2 s bis 60 s) beim nächsten Rendern erneut (`asksDistro`, `distroAnswered`). Der Baum (`explorer-tree.ts`, rein) listet Ordner beim Aufklappen über `files.list`; jede Ladung hat ein Token, ein neuer Baum für einen neuen Schlüssel (Session, Backend, Distro, Pfad) zählt weiter, also verwirft `finishLoad` veraltete Antworten. Der Baum liegt in einer Ref, damit eine späte Antwort gegen den gezeigten Baum geprüft wird. Tasten und Klicks (`explorer-keys.ts`), Zustände, Texte und Breite (`explorer-view.ts`) sind rein. Der Baum hält den Fokus als Ganzes (`aria-activedescendant`) und hält seine Tasten mit `stopPropagation` vom Fenster-Handler fern; Escape ruft `refocus`. Kürzel `Ctrl+Shift+X` (ein/aus, auch Menü „Ansicht“, Event `toggleExplorer`; der Fokus bleibt im Terminal) und `Ctrl+Shift+O` (Fokus; ein Wunsch, den das Panel einmal einlöst, sobald es den Baum oder einen Text zeigt, `focusStep`; `refocus`, Escape, Ausblenden und ein Druck ins Pane lassen ihn verfallen). Mit dem Fokus im Panel tun `copy` und `paste` nichts (`leavesKey`), sonst schriebe der Fenster-Handler in die Shell. Sichtbarkeit und Breite (180 bis 640 Pixel, Panes mindestens 240, auch per CSS `max-width` beim Verkleinern des Fensters) stehen im Fenster des Layouts (`explorerVisible`, `explorerWidth`, Protokoll 1.9); lehnt ein Core 1.8 sie als unbekannte Felder ab (genau diese Meldung; die Version aus `hello` gibt die Client-Bibliothek nicht heraus), speichert der `LayoutCoordinator` sofort noch einmal ohne sie (`withoutExplorer`), ohne einen Versuch für Revisionskonflikte zu verbrauchen, und sendet sie diesem Core nicht mehr; jede neue Core-Verbindung (`coreConnected`) setzt das zurück. Im Screenshot-Modus öffnen neue Fenster ohne Panel, weil andere Gruppen Sessions in `~` zeigen; die Leck-Prüfung liest Kopfzeile und Zeilen des Panels mit und lehnt dort `/home/<name>` ab. Dateiaktionen (#203): Die Regeln stehen rein in `explorer-actions.ts` (Menü je Backend und Typ, geschützte Orte, Drop-Ziele, Texte, Baum nach einer Aktion) und `path-quote.ts`. Menü (`ContextMenu`) und Lösch-Dialog (`ConfirmDialog`) hängen per Portal an `document.body`, und der Escape-Handler des Panels nimmt nur Ziele in seinem DOM, weil React Ereignisse eines Portals an die React-Eltern weitergibt. Umbenennen ist ein Feld in der Zeile, das alle Tasten bei sich hält. Ziehen nutzt den `DragProvider` des Fensters (Payload `explorer-entry`, Ziele `explorer:<pfad>`). „Pfad kopieren“ schreibt über `navigator.clipboard`; „Pfad ins Terminal einfügen“ geht nur an das Pane aus `pastePaneId` (das gefolgte Pane, wenn es schreibt) über `TerminalController.paste`, quotiert, ohne Steuerzeichen und ohne Enter; das Pane wird danach aktiv und fokussiert.
- **Screenshot-Modus** (`--screenshot <dir>`): Die App startet einen eigenen Core mit eigener Pipe (`TERMDOCK_PIPE`), Datenbank in einem Temp-Verzeichnis (`TERMDOCK_DATA_DIR`) und einem tmux-Socket des Laufs `termdock-test-<pid>-<nonce>` (`TERMDOCK_TMUX_SOCKET`), nutzt ein eigenes Electron-Profil je Prozess im Temp-Verzeichnis (`termdock-screenshot-profile-<pid>`, Profile beendeter Läufe entfernt der nächste Lauf) und keine Einzelinstanz-Sperre. So laufen mehrere Screenshot-Läufe und die WSL-Tests auf `termdock-test` parallel, ohne sich Sessions zu beenden. Sie legt fünf Sessions an, bringt sie in die Zustände `Running`, `Detached`, `Exited` (`exit`) und `Interrupted` (`tmux kill-session` über `wsl.exe` auf dem Socket des Laufs), öffnet sie per Klick im Renderer als Tabs, speichert die Fenster (Sidebar, eingeklappte Sidebar, leeres Fenster mit Formular, Hinweis-Tab, Leser; seit #27 in einem dritten Fenster dieselbe Session in zwei Panes, seit #66 per Umschalt+Klick mit gezoomtem und beschnittenem Leser, Teilen per Knopf in eine neue Session, einfachem Klick ohne Wechsel von Schreiber und tmux-Größe und Übernahme per Knopf und Doppelklick, `stty size` vor und nach dem Ziehen eines Trenners mit echten Mausereignissen über `webContents.sendInputEvent`, 3 und 4 Panes, `vim` vor und nach Teilen und Ziehen samt Prüfung der Cursorposition gegen tmux) per `webContents.capturePage()` als PNG und beendet danach mit `core.shutdown { stopSessions: true }` alle Sessions und den Core. Scheitert schon das Verbinden oder die erste Antwort, beendet sie den gestarteten Core ebenso, notfalls über seine Prozess-ID, und wartet auf sein Ende, bevor sie das Datenverzeichnis entfernt. Seit #63 legt sie in einem eigenen Fenster über den Dialog und den Core Workspaces und ein Projekt an, ordnet Sessions zu, archiviert und löscht eine eigene Session, zieht eine Session mit echten Mausereignissen auf einen Workspace (Hervorhebung, Abbruch mit Esc, Prüfung der Session im Core), öffnet das Kontextmenü per Rechtsklick und Umschalt+F10, verschiebt per Pfeiltasten und Enter und prüft den Platzhalter einer gelöschten Session im offenen Tab. Danach (#29) schließt sie alle Fenster, legt zwei Fenster mit mehreren Tabs, Splits, eingeklappter Sidebar und einer später mit `tmux kill-session` beendeten Session an, speichert, startet die Oberfläche neu (Fenster schließen, frischer Coordinator, `layout.get`, Fenster öffnen wie beim Start) und vergleicht Tabs, Panes, Anteile, aktive Elemente und Bounds mit dem Zustand davor. Der Produktiv-Socket `termdock` wird nie berührt.
- **Tastenkürzel und Zwischenablage (#28):** Eine Keymap (`keymap.ts`, Befehl → Kürzel, Standardbelegung) und ihre Auflösung (`event.code` plus exakte Modifikatoren) sind rein und getestet; kein Standardkürzel ist `Ctrl+<Buchstabe>` ohne Shift, damit Shell, tmux und TUIs ihre Tasten behalten. Gebundene Tasten fängt der `TerminalController` über `attachCustomKeyEventHandler` ab (Befehl einmal je keydown, `preventDefault`, nicht an xterm.js), ein Fenster-Listener deckt den Fokus außerhalb des Terminals ab; `Ctrl+Shift+N` bleibt dem Menü-Accelerator des Main. Befehle (`commands.ts`) laufen auf den Store-Aktionen, der Pane-Fokus nach Geometrie (`pane-focus.ts`). Die Zwischenablage nutzt `navigator.clipboard` des Renderers (Sonde mit `sandbox` und `contextIsolation`: Text mit Umlauten und Zeilenumbruch gelesen und geschrieben; Electron erteilt der eigenen Seite die Rechte, ein künftiger Permission-Handler muss sie erlauben), also kein neuer Brückenaufruf. Einfügen geht durch `Terminal.paste` (CR statt Zeilenumbruch, Bracketed Paste nach Anforderung der Anwendung; xterm.js 6.0.0 setzt die Marker selbst) und nur in der schreibenden View (`TerminalController.paste`); ein Leser liest die Zwischenablage nicht und meldet den Grund in der Statusleiste. Die Übersicht der Kürzel ist ein Dialog aus der Keymap.
- **Einstellungsdialog (#64):** `Ctrl+,` ist ein Befehl der Keymap (`openSettings`, Taste `Comma`), damit er auch im Terminal greift; der Menüeintrag „Datei → Einstellungen …“ zeigt das Kürzel mit `registerAccelerator: false` und schickt `openSettings` an das fokussierte Fenster. Die Brücke bekommt sieben Aufrufe (`getSettings`, `updateSettings`, `listProfiles`, `createProfile`, `updateProfile`, `deleteProfile`, `listDistros`; der Main prüft Form, bekannte Schlüssel, mindestens eine Änderung und nicht leere IDs, der Core die Werte) und zwei Events an alle Fenster (`settingsChanged`, `profilesChanged`). `SettingsDialog.tsx` hält Einstellungen, Profile und Distributionen selbst (geladen beim Öffnen, aktuell über die Events; ein Event gewinnt gegen eine spätere Antwort), ein offenes Formular behält seine Eingaben (alle Abschnitte bleiben eingehängt und sind nur `hidden`, die Fokusfalle überspringt versteckte Teile; neue Einstellungen gehen nur in unberührte Felder, `rebaseGeneral`/`rebaseHistory`; Escape im Profil-Editor führt erst zur Liste zurück; das Menü-Event öffnet nichts, solange ein anderer modaler Dialog offen ist). Abschnitte: Allgemein (Distribution aus `wsl.distros`, sonst freies Feld mit Grund; Standardshell; Standardverzeichnis; „Beim Schließen fragen“), Verlauf (Limit in MiB, Standard an/aus, Hinweis auf die Platte), Kürzel (Übersicht der Keymap, nur lesen), Startprofile (Liste, Editor, Löschen mit Rückfrage in der Zeile; Befehl ein Argument je Zeile, Umgebung `NAME=Wert`; Workspace und Projekt bleiben beim Bearbeiten). Die Prüfung und die Patches (nur geänderte Schlüssel, leeres Feld → `null`) sind reine Funktionen in `settings-form.ts`; die Secret-Prüfung der Umgebung bleibt im Core, der Dialog zeigt dessen Meldung. Die Fokusfalle nimmt seitdem `select` und `textarea` auf. Neue Sessions und Profil-Sessions ohne `distro` bzw. `shell` bekommen `defaultDistro` bzw. `defaultShell` der Einstellungen im Core (`launchDefaults`). Die Screenshot-Szene (`screenshot-settings.ts`) öffnet per `Ctrl+,` und über das Menü-Event, nimmt alle Abschnitte, Editor, Liste und die Ablehnung eines Profils mit `API_TOKEN` auf und prüft jede Änderung im Core.

## Folgen

- Jede Erweiterung der Brücke braucht eine Prüfung im Main (`coreStatus` und `sessionCreated` aus #26 haben sie).
- Je Pane ein `TerminalController` (#27); die Brücke verteilt Events je Fenster und Session, zwei Views derselben Session im selben Fenster trennt die Sequenzmarke (Restlücke #34).
- `npm ci` lädt das Electron-Binary; Tests und Typecheck brauchen es nicht.
- Electron lädt beim Import von `@termdock/core` auch node-pty und `node:sqlite`; beides läuft unter Electron 45 (ADR 0003, 0004). Ein Unterpfad-Export nur für den Client würde das vermeiden.
- Ein Absturz des Core trennt alle Fenster nur kurz: Der Main startet ihn neu, die Fenster hängen ihre Views neu an (#130). WSL-Sessions kommen mit ihrem Snapshot zurück, Windows-Sessions werden `Interrupted` (ADR 0001). Ein Layout-Speichern während des Neustarts scheitert und folgt erst mit der nächsten Änderung.
