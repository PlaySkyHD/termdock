# Design

## Context

`runCore` belegt die Pipe, öffnet die Datenbank, gleicht die gespeicherten Sessions ab (`SessionRegistry.restore`) und löst dann `ready` auf; bis dahin warten alle Anfragen außer `hello` (ADR 0001). Profile liegen in `launch_profiles`, Sessions tragen `profileId` (#58). `session.create` mit `profileId` baut den Start über `ProfileService.launchFor` (Spec des Profils, `cwd: "~"` über `defaultCwd`, Verlauf-Schalter, Workspace). `SessionRegistry.create` trägt eine Session synchron in `Starting` ein, speichert sie, meldet `onCreated` (→ `session.created`) und startet sie danach asynchron.

## Goals / Non-Goals

**Goals:** Jedes Autostart-Profil hat nach dem Core-Start genau eine lebende Session; kein Doppelstart bei Core-Neustart oder mehreren Clients; ein nicht erreichbares Backend wird einmal gemeldet.

**Non-Goals:** Autostart beim Anlegen oder Ändern eines Profils zur Laufzeit, automatische Wiederholung, UI.

## Decisions

- **Eigenes Modul, Aufruf nur aus `run-core.ts`.** `runAutostart({ registry, profiles, settings, backends, knownUnavailable, cancelled, report })` in `session/autostart.ts`. Es gibt keine IPC-Methode dafür; ein Client kann den Autostart weder auslösen noch wiederholen. `runCore` ruft es genau einmal nach `restore()` auf. Damit ist „einmal je Core-Start“ eine Eigenschaft des Aufrufers, nicht eines Zustands in der Datenbank.
- **Erkennung über die Registry.** Lebend heißt `Starting`, `Running` oder `Detached` nach dem Reconcile (`registry.list()` mit gleicher `profileId`). Eine WSL-Session, die den Core-Neustart überlebt hat, ist nach dem Reconcile `Detached` und verhindert den Start. `Exited`, `Interrupted` und `Archived` zählen nicht; die alte Session bleibt unverändert, die neue bekommt eine neue ID. Die Registry ist die Quelle, nicht eine eigene Abfrage über den Index `sessions_profile`: Sie enthält nach dem Reconcile genau die gespeicherten Sessions mit ihren abgeglichenen Zuständen.
- **Gleiche Logik wie `session.create`.** Die Abbildung „Profil → Eingabe von `registry.create`“ (`launchFor`, `profileId`, Workspace und Verlauf-Schalter des Profils, Vorrang der Anfrage) steht einmal in `ProfileService.sessionInput`; der Server ruft sie für `session.create` mit `profileId`, der Autostart mit `{ name: profile.name }`. `runCore` baut dafür einen eigenen `ProfileService` über dieselben weiterleitenden Repositories wie der Server; der Dienst ist zustandslos.
- **Anfragen warten auf das Eintragen, nicht auf den Start.** `ready` löst erst auf, wenn alle Autostart-Sessions eingetragen sind. `registry.create` trägt synchron vor dem ersten `await` ein; der Autostart ruft es für alle Profile, ohne auf die Starts zu warten. Begründung: (1) Jeder Client sieht die Autostart-Sessions in seiner ersten `session.list`, zwei Fenster sehen denselben Stand und keines kann eine Lücke als „fehlt, also anlegen“ deuten. (2) Kein Client-Aufruf läuft parallel zum Autostart: `profile.update`/`profile.delete` ändern nicht das gerade gelesene Profil, und `core.shutdown { stopSessions: true }` erfasst die Autostart-Sessions (sie sind `Starting`, der Shutdown wartet auf sie), statt dass ein später Start eine tmux-Session hinterlässt. (3) `core.status` nennt ein vom Autostart gefundenes, nicht erreichbares Backend schon bei der ersten Anfrage. Kosten: die Erreichbarkeitsprüfung je Backend (`wsl.exe … tmux -V`) verzögert die erste Antwort; ein langsamer Start (tmux, Shell) verzögert sie nicht. Alternative „ready nach dem Reconcile, Autostart danach“ verworfen: Sie bräuchte einen eigenen Abgleich mit Shutdown und Profiländerungen und brächte nur ein früheres `session.list`.
- **`session.created`.** Der Autostart legt über `registry.create` an; der Server meldet jede so angelegte Session an alle Verbindungen, die `session.list` genutzt haben. Weil Anfragen bis nach dem Eintragen warten, hat beim Core-Start noch kein Client gelistet; Clients lesen die Sessions mit `session.list` und sehen danach `session.stateChanged`. Der Vertrag bleibt derselbe wie für jede neue Session.
- **Nicht erreichbares Backend.** Vor dem Eintragen prüft der Autostart je benötigtem Backend einmal `available()`; was der Reconcile schon als nicht erreichbar gemeldet hat (`RestoreResult.backendUnavailable`), wird weder erneut gefragt noch erneut gemeldet. Fehlt das Backend oder ist es nicht erreichbar, legt der Autostart für dessen Profile keine Session an (keine `Interrupted`-Leiche je Core-Start), meldet eine Zeile `autostart: backend_unavailable: <kind> …` auf stderr und trägt das Backend über die neue Methode `SessionRegistry.reportBackendUnavailable` für `core.status` ein. Scheitert ein Start trotz erreichbarem Backend (z. B. eigene Distro des Profils), setzt die Registry die Session `Interrupted` und der Autostart meldet den Fehler einmal je Profil. Keine Wiederholung: der nächste Versuch ist der nächste Core-Start oder ein Neustart durch den Nutzer.
- **Abbruch.** Wird der Core während der Prüfung geschlossen (`cancelled()`), legt der Autostart nichts an. `runCore` wartet auf den Autostart wie auf den Reconcile mit `Promise.race` gegen das Schließen. Der Autostart wirft nie; ein Fehler beim Lesen der Profile wird gemeldet und der Core startet ohne Autostart.
- **`registry.ts`.** Nur eine neue Methode am Klassenende (`reportBackendUnavailable`); `create`, `restore` und die Output-/Redraw-Stellen (#88) bleiben unberührt.

## Risks / Trade-offs

- Ein Autostart-Profil mit eigener Distro, die nicht existiert, erzeugt je Core-Start eine neue `Interrupted`-Session. Die Prüfung `available()` deckt nur die Standard-Distro ab; eine Prüfung je Distro wäre ein Eingriff in die Backend-Schnittstelle (nur Orchestrator).
- Die erste Antwort an Clients wartet zusätzlich auf eine Erreichbarkeitsprüfung je Backend der Autostart-Profile, auch wenn der Reconcile dasselbe Backend gerade erreicht hat (`RestoreResult` nennt nur nicht erreichbare Backends). Nach dem Reconcile läuft WSL bereits, die zweite Prüfung ist kurz.
- `registry.create` muss die Session vor seinem ersten `await` eintragen; der Test „registers the sessions before it resolves“ und der Zwei-Client-Test in `run-core.test.ts` schlagen fehl, wenn sich das ändert.
