# Design

## Context

`Settings`, `SettingsPatch`, `validateSettings`, die Stubs und die Tabelle `settings` (Migration 3) stehen seit #55. Der Main verlässt die App über `before-quit` (Menü, `app.quit()`) und `window-all-closed`; beides speichert das Layout (`finishLayoutAndClient`) und beendet nur die Verbindung (ADR 0001).

## Goals / Non-Goals

**Goals:** Eine Entscheidung „fragen oder nicht“ als reine Funktion; ein Dialog im Fenster (damit ein Screenshot ihn zeigt); die Wahl bleibt im Core gespeichert.

**Non-Goals:** Einstellungsdialog (#64), Verlauf (#59), Tray.

## Decisions

- **Einstellungen im Core.** `SettingsRepository.get()` ist synchron und gibt immer ein vollständiges `Settings` zurück (fehlender Schlüssel = `DEFAULT_SETTINGS`), damit der HistoryStore (#59) es später je Nutzung lesen kann. Ein nicht lesbarer oder ungültiger Wert wird gemeldet (`onLayoutInvalid`, wie beim Layout) und durch den Standard ersetzt; ein kaputter Eintrag blockiert nicht jedes `settings.get`. Unbekannte Schlüssel in der Tabelle werden ignoriert. `set` liest, prüft und schreibt unter `BEGIN IMMEDIATE`; `null` löscht die Zeile. `applySettingsPatch` ist rein und prüft das Ergebnis mit `validateSettings` (`bad_request`), obwohl der Guard den Patch schon prüft. Der Server nimmt das Repository als optionale Option (Standard: In-Memory), damit andere Tests unverändert bleiben.
- **Event nach der Antwort.** `settings.set` antwortet mit den zusammengeführten Einstellungen; danach geht `settings.changed` an alle Listen-Clients, auch den Aufrufer (`notifyListers`).
- **Dialog im Renderer statt `dialog.showMessageBox`.** Nur so zeigt `capturePage()` ihn; der Rest der App bleibt eine Web-Oberfläche. Der Main schickt dem fokussierten Fenster das Event `quitRequested { requestId, activeSessions }`; der Renderer antwortet mit `answerQuit { requestId, choice, remember }`. `QuitPrompt` hält höchstens eine offene Frage, nimmt nur die Antwort des gefragten Fensters mit der richtigen ID an und wertet ein verschwundenes Fenster (geschlossen, neu geladen, abgestürzt) als „Abbrechen“. Eine zweite Anfrage bekommt die Antwort der ersten (kein zweiter Dialog). Ein unbekanntes Fenster bricht sofort ab; eine Frage, die gesendet wurde, bevor die Seite lud, geht nach `did-finish-load` erneut hinaus (der Renderer nimmt sie idempotent), damit das Beenden nie auf einen Dialog wartet, den niemand sieht. Escape gilt im ganzen Fenster, ein Klick neben den Dialog nimmt ihm den Fokus nicht.
- **Zustellung bestätigt, Zeitlimit = Abbrechen.** `sendTo` meldet nur „Fenster bekannt“, nicht „Renderer hört zu“. Der Renderer bestätigt deshalb mit `quitShown`, sobald der Dialog steht; bis dahin sendet der Main die Frage alle 500 ms erneut (und nach `did-finish-load`). Kommt binnen 5 s keine Bestätigung, gilt die Frage als „Abbrechen“. Begründung: „Abbrechen“ ist die einzige Folge ohne Datenverlust und ohne Überraschung (die App bleibt offen, nichts wird beendet, der Benutzer sieht, dass nichts passiert, und kann erneut beenden); „Sessions behalten“ würde die App ohne sichtbaren Dialog schließen, „Sessions beenden“ gar Sessions ohne Wissen des Benutzers. Nach der Bestätigung gibt es kein Limit, der Benutzer antwortet, wann er will. Der Renderer merkt sich beantwortete Fragen, damit eine verspätete Wiederholung den Dialog nicht neu öffnet.
- **Ablauf ohne Electron.** Entscheidung (`decideQuit`) und Beenden (`QuitFlow`: letztes Fenster halten, `before-quit`, Speichern, `core.shutdown`, Verbindung schließen, `app.quit()`) liegen in `quit-flow.ts` mit eingespeisten Abhängigkeiten und sind getestet (Reihenfolge, Abbrechen, doppeltes Beenden, Fehlerpfade). `core.shutdown` geht erst nach dem Speichern hinaus. Das Speichern und Schließen läuft einmal; ein späteres `stopSessions` zählt, solange der Shutdown noch nicht gesendet ist (der Wunsch wird nach dem Speichern gelesen); danach ist die Verbindung zu, das Versäumnis wird geloggt statt verschluckt. `session-end` geht über `planQuit("session-end")` (fragt nie, behält die Sessions), ohne `app.quit()`.
- **Fokus-Fang.** `aria-modal` hält den Fokus nicht: Tab und Umschalt+Tab wandern im Dialog im Kreis (`nextFocusIndex`), ein Fokus, der nach außen springt, kehrt zurück. So erreichen keine Tasten das xterm dahinter.
- **Entscheidung rein und geteilt.** `planQuit({ reason, activeSessions, settings })` liefert `quit` (mit `stopSessions`) oder `ask`: ohne Session in `Running`/`Detached` und bei `session-end` nie fragen und nie beenden; sonst fragen, solange `confirmQuitWhileRunning` gilt, sonst die gespeicherte Aktion (fehlend = `keepSessions`). `outcomeOfAnswer` macht aus der Antwort ein Ergebnis; „Abbrechen“ speichert auch mit gesetzter Checkbox nichts. Der Main zählt die Sessions mit `session.list` kurz vor der Entscheidung, nicht aus dem Renderer-Zustand.
- **Ablauf im Main.** `before-quit` (nicht `quitReady`) hält an und startet `requestQuit`; der `close`-Handler des letzten Fensters hält das Schließen an und startet es ebenfalls. Bei „Abbrechen“ ändert sich nichts (Fenster bleiben, Layout unverändert). Ist das Beenden entschieden, bleibt der Ablauf gesetzt (Speichern und Shutdown laufen noch), eine weitere Anfrage startet keine zweite Entscheidung. Sonst: alle Fenster im Layout behalten, Layout speichern (3 s), bei `stopSessions` `core.shutdown { stopSessions: true }` (normale Zeitgrenze der Brücke), Verbindung schließen, beenden. Der erste Aufruf von `finishLayoutAndClient` legt `stopSessions` fest. Scheitert die Entscheidung (Core antwortet nicht), beendet die App wie bisher und behält die Sessions: nie den Benutzer einsperren. Ein Core ohne `settings.get` (Protokoll 1.2) wird mit den Standardwerten behandelt.
- **Standardfokus** liegt auf „Oberfläche schließen, Sessions behalten“ (bisheriges Verhalten, nicht zerstörend); Escape bricht ab, ein Klick auf den Hintergrund tut nichts. Solange der Dialog offen ist, laufen die Tastenkürzel des Fensters nicht.
- **Screenshot-Modus.** Der Lauf schließt keine Fenster über den Dialog (`shotDir` ausgenommen); die Szene ruft `decideQuit` auf einem Fenster auf, klickt wie ein Benutzer und prüft Antwort und gespeicherte Einstellung im isolierten Core.

## Risks / Trade-offs

- Zwei Anfragen (`session.list`, `settings.get`) verzögern das Beenden um wenige Millisekunden; bei hängendem Core greift der Timeout der Brücke (10 s) und die App beendet wie bisher.
- „Sessions beenden“ beendet auch den Core (`core.shutdown`); andere Clients verlieren die Verbindung. Das ist der gemeinte Zweck.
